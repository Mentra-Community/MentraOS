The October 15 Google request was selected and accepted on Mini Mac, but the existing executor guard rejected it before launch. Its 5 GiB output reservation plus 2 GiB safety margin required 7,516,192,768 bytes; all 184 observations during the wait were below that floor. An idle lane was insufficient evidence of capacity.

This change adds one measured attribute to the existing recorder resource, rather than another resource kind or registry. The prepared recorder requirement carries minimumAvailableBytes derived from its frozen execution policy. Recorder offers carry a common per-host disk pool identity, actual observation timestamp, available bytes, staging headroom and the remaining output reservations of exact locally accepted requests.

Before emitting device runner labels, Core picks a compatible host/lane and retains its byte claim on the existing test_host_state resource record; test_requests retains only the selected target/receipt. Atomic compare-and-swap checks both the host observation sequence and resource-claim version, so concurrent preparations and host reports conflict/retry through that row. Another lane cannot spend the same bytes. A host claim left by a failed request-link write converges after a valid immutable receipt selects another host, even if the winner has already bound or refused preparation; any reported local custody still retains the losing claim. Exact locally observed request/input reservations are not counted twice. Missing, future and older-than-two-minute observations fail closed. Cancellation does not release delivered capacity until actual cleanup and a subsequent measurement; unbound durably canceled work releases its claim. Bound pre-executable refusals cannot produce an executable completion digest. Their authenticated terminal preparation rejection/cancellation must match the retained host/lane and immutable intent, then a later measured offer must contain no local reservation before their claim releases. A terminal state or generic fleet cancellation alone is insufficient. Unknown or missing request evidence remains conservative until normal reconciliation. Both physical free bytes and the existing evidence staging pool are checked.

GitHub does not support arbitrary numeric resource labels. Its existing host/lane labels therefore target the retained reservation. Core rechecks the same offer before binding; the existing native executor capacity check remains the final protection against disk changes after the observation. The source policy and current 2 GiB margin are unchanged.

A request accepted locally but subsequently blocked by a capacity race now exposes storage-capacity in run.inspect and its existing heartbeat. Admin and PR checks show Waiting to start with the actual block observation timestamp. They do not invent an executor, owner generation, startedAt, completed steps or a passing result.

Rollout requires both reviewed Core and Harness changes. Deploy Core's accepting schema and reservation policy first, then the normal framework publisher and safe idle acceptance. An unbound prepared request derives capacity from its already frozen recording policy without rewriting its definition, requirements or digest; it acquires the same host claim before binding. Already-bound work remains unchanged. Old controllers publish no measured recorder offer and therefore cannot receive newly bound recording work; there is no old-version capacity fallback. After normal API41 acceptance, verify actual same-pool recorder offers, durable target receipts and atomic host claims before the single original-Google linked verification. Normal tests are separate from physical fleet/deployed qualification.
