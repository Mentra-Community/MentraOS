# Fresh phone backend prerequisite

An Android routine declaring the existing phone `backend-connectivity` capability must have a fresh, target-specific observation before Core selects that phone. A static installed capability or host internet connection is insufficient. The selected APK remains the only authority for the backend origin. A shell default-network/TCP witness proves neither the app's HTTP/CDN route nor future connectivity; `appRouteVerified` remains false and product assertions remain unchanged.

Use only the existing typed resource offers, qualification target delivery, host-row `resourceReservations` CAS, local resource rows, sealed reader journal, native closure receipts and normal cancellation/return transport. No resource registry, endpoint, credential store or monitor service is added.

1. Existing bounded qualification target discovery may offer structurally suitable Android candidates without choosing a product winner. Each candidate preserves the exact app archive/receipt/source, routine source, original deadline and request identity. No prerequisite may stage or rewrite `fleetResourceAdmission` or `fleetTarget`.
2. The host verifies the pinned APK configuration before obtaining device custody. A missing or unsupported target is unknown. Controller service URLs, channel labels and fixtures cannot supply a replacement target.
3. A capability-scoped existing resource check acquires the exact phone row without inventing a lane owner. The existing Core reservation intent has a narrow prerequisite purpose for that original target, current controller and phone. Its raw-phone claim uses the same host-row CAS. Probe acquisition rejects retained ordinary run claims for that lane; ordinary allocation rejects probe claims before staging a candidate. Backend-dependent run admission retains its existing recorder byte claim on that same host row before the existing request CAS stages a candidate. The request CAS selects one immutable host/lane; a provisional claim alone never authorizes execution. Lost transport preserves the original intent or byte claim for observation/adoption, without another acquisition or alternative candidate. No cross-collection transaction or database-specific fallback is required. Multiple provisional claims observed on distinct hosts fail closed and retain custody; the request CAS still prevents a second executable candidate.
4. The check seals its exact reader roster, command/input digest, tool and phone before dispatch. One bounded read observes boot identity, default-network state and TCP reachability to the verified hostname. Cancellation, source/controller change, target replacement or expiry cannot authorize a child or publish positive health.
5. Capability failure is separate from physical idle. A parsed negative result may release read custody after every original reader closes; an unknown child retains custody until original closure. Release appends a real resource-check release event and existing Core return receipt. It never synthesizes a lane release, physical restoration or old idle-contract pass. Original unknown outcomes remain immutable even if later transport settlement permits release.
6. Core selection and the local pre-allocation check consume only qualified, released, current-source/controller/phone/build/target observations within 120 seconds. Resource generation invalidates prior health after another owner. Negative or expired health withdraws backend eligibility only; offline routines, safe cleanup and other resources remain independent. The execution-time selected-app-process guard still measures before credentials/actions.

The bounded implementation performs one attempt for each immutable request target and accepted source. It does not refresh staged, bound or already accepted Android work. If later source preparation or admission consumes the observation's 120-second freshness allowance, the original request stays blocked before app setup through its original deadline. This availability limit must be visible in release validation; a new source requirement for strictly unstarted accepted work would need exact executable-input and no-reader authority rather than an automatic repeated probe. Phones with a physical idle contract are also excluded from this capability check: their existing custody/restoration qualification is not invalidated or replaced.

Core deployment must wait for matching API61 host source acceptance and paired contract review. Source tests establish claim and cancellation behavior, not live phone readiness, database deployment compatibility, an original network cause, or an app HTTP/CDN route guarantee.

Required offline tests cover probe/run claim races in both directions, response loss/restart, exact APK/target/phone/source/generation mismatches, future/expired/unknown health, cancellation during verification/claim/read/export, missing or extra roster members, late results after expiry, and negative health releasing read custody without changing idle/repair behavior. A source PR or CPU fixture is not device qualification or proof of any original network cause.
