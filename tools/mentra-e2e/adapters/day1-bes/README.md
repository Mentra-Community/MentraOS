# Compact January BES setup adapter

This extracts the supervised compact-BES setup path into a callable adapter for
`runLifecycle`. It uses the existing ASG debug receiver, artifact validation,
identity checks, native owner admission and eight-minute observer. It does not
implement another OTA protocol, acquire another lease, restart ASG, reconnect
ADB, or retry a firmware dispatch.

The only target is the qualified compact January `17.26.1.13` artifact. Both
artifact hashes and the existing `verify_ota_build.py` hash are fixed in
`config.py`; private paths must be supplied. The raw image must be exactly
1,966,076 bytes (strictly below 1,966,080), and its OTA image 1,131,730 bytes.
No firmware, credentials, fixture identities or executable binaries are stored
here. Parameterizing a different source identity does not qualify that hardware,
ASG build or firmware combination.

## Inputs and invocation

The trusted local worker writes a mode-0600 JSON file with these exact fields:

| Field | Content |
| --- | --- |
| `schemaVersion`, `profileId` | `1`, `compact-january-bes-v1` |
| `fixture` | `{cid, mac, serial_aliases, transport: {kind: "network", address}}`; full eMMC CID and uppercase BLE MAC, explicit serial aliases and previously verified RFC1918 IPv4 endpoint on port 5555 |
| `expected` | `{boot_id, slot, mtk, bes, asg_version_code, asg_apk_sha256}`; exact current source identity |
| `target` | `{version: "17.26.1.13", raw: {path, sha256}, ota: {path, sha256}}` |
| `tools` | `{adb: {path, sha256}, python: {path, sha256}, verifier: {path, sha256}}`; Python 3.11+ and the qualified existing verifier |
| `sourceProof` | `{log: {path, sha256}, pid, deviceEpoch}`; frozen mode-0600 native epoch log with fresh UART version and readiness proof |
| `proof_max_age_seconds` | Integer 1–60, checked again against actual device time immediately before dispatch |
| `lease` | `{path, ownerPid}`; the existing fixture lease, owned by the immediate parent process |
| `claimsRoot` | Existing owned mode-0700 directory shared across lifecycle runs |
| `definition` | SHA-256 for every filename in `config.FILES`, including the reconciler |

All paths are absolute and all hashes lowercase SHA-256. Config, source logs,
claims and receipts stay private. Native `IDLE` or actual `SUCCESS/verified`
source state is derived from the log; a caller cannot supply a made-up settled
owner. A prior successful owner's verification boot can precede the current MTK
boot, provided the current version and UART readiness are freshly observed.

The lifecycle process launches the pinned Python binary directly, without an
intermediate shell or lease-owning child:

```text
<PINNED_PYTHON> <ADAPTER_DIR>/run.py observe \
  --config <PRIVATE_CONFIG> --config-sha256 <CONFIG_SHA256> \
  --owner <LIFECYCLE_MUTATION_UUID> --run <NEW_OBSERVATION_DIRECTORY>

<PINNED_PYTHON> <ADAPTER_DIR>/run.py install \
  --config <PRIVATE_CONFIG> --config-sha256 <CONFIG_SHA256> \
  --owner <LIFECYCLE_MUTATION_UUID> --run <NEW_ATTEMPT_DIRECTORY>
```

`observe` performs read-only device commands and writes local evidence only.
`install` reserves a fsynced shared claim keyed by CID, source boot and target
artifact before entering the observer. It creates durable transfer and install
intents before the corresponding single push and single receiver broadcast.
Every write rechecks the parent lease, current source identity and active APK.
Changing the owner or output directory cannot bypass an existing claim.

The native owner is generated by the ASG receiver. It is distinct from the
lifecycle UUID and is bound through the actual `artifact=setup-<UUID>` log.
Accepted authorization, accepted apply, apply acknowledgement and new-boot
`SUCCESS/verified` must refer to that native owner. Command output, elapsed time,
transport readbacks and original failure outcomes remain in the attempt folder.
A normal successful install still reports setup-only, with the fixture not ready
for other routines.

## Pure reconciliation

`reconcile.reconcile(config, attempt_directory, lifecycle_owner, current)` is a
read-only file/evidence function. It runs no subprocesses or hardware commands.
A trusted callback under the existing lifecycle lease supplies `current`, never
an untrusted CI request:

```text
{
  startedAt, finishedAt,             // host epoch seconds, <=30-second fresh batch
  bootBefore, bootAfter,
  pidBefore, pidAfter, startTicksBefore, startTicksAfter,
  endpoint,                         // exact configured endpoint
  observed: {
    boot_id, serial, cid, mac, mtk, slot, asg_version_code,
    apk_sha256, pid, device_epoch
  },
  log: {path, sha256}, logCapturedAt  // frozen private native epoch log in batch
}
```

The callback must actually bracket identity and process reads around its log
capture. It must not turn an old record into a fresh one by changing timestamps.

The result is one of `settled` (exact source before any claim), `active`,
`satisfied` or `unknown`. Missing or ambiguous proof stays `unknown`, never
permission to resend. `satisfied` requires the immutable original claim/intent,
actual same-owner accepted install trace, matching current identity and fresh
new-boot native `SUCCESS/verified`, without later admission. An actual
`version_proof_complete result=APPLIED` must also exist; an ordinary query cannot
manufacture completion.

A satisfied result contains `continuityInput`, the existing
`day1-setup/bes_continuity.py` input shape. The caller can save this JSON privately
and use its hash as the full-January setup input. Its referenced logs and intent
must remain unchanged. This is an accepted-install input for subsequent MTK-only
continuity checks, not a fresh post-wipe BES measurement or customer OTA pass.
The reconciler never overwrites an original failed result.

## Recovery and qualification boundary

The supervised private runs established the compact artifact and native path,
but also encountered loss of the durable apply-pending state and UART recovery
timeout. A separately supervised normal-reader restart then produced actual
same-owner success. That restart has **not** been promoted into this adapter.
Loss of network ADB after reboot also requires separately owned transport
recovery; the observer only re-observes the configured endpoint when it returns.

An unsettled attempt therefore keeps its claim and recovery-required evidence.
The orchestrator must preserve that outcome and defer further mutations until a
trusted observation or separately qualified recovery settles it. No automatic
claim deletion, source-state reset, reboot, reader restart or second firmware
attempt is available here. The extracted tracked flow still needs a complete
hardware pass before unattended use; offline tests do not supply that evidence.

Run the focused tests without touching hardware:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover \
  -s tools/mentra-e2e/adapters/day1-bes -p 'test_*.py'
```
