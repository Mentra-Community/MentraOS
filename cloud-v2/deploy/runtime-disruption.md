# Runtime voluntary disruption across release environments

At 20:44:13 UTC on 14 October 2026, Karpenter evicted the sole dev Runtime pod for underutilization consolidation. The replacement became available at 20:44:34; two original Mentra App processes received HTTP 503 from `/api/client/min-version` in that interval. The Application node group's cost optimization is enabled. The eviction was a deliberate consolidation decision, not evidence of a Runtime crash or OOM.

Keep Runtime at one replica and its existing CPU/memory requests. The source-owned `deploy/runtime-policy.yaml`, rendered for dev, staging and production, sets the existing Runtime Helm chart's PodDisruptionBudget to `minAvailable: "100%"`. At one desired replica this leaves no allowance to voluntarily evict the only healthy Runtime. Karpenter respects this budget when choosing consolidation candidates. Other workloads and node-pool settings are unchanged; there is no new placement rule or steady-state capacity request.

Application rollouts are distinct from node evictions. The Deployment uses `maxUnavailable: 0` and `maxSurge: 1`: it can start a temporary replacement, wait for readiness, then remove the old pod through the Deployment controller. PodDisruptionBudgets do not block those controller-managed rolling updates. The existing readiness probe and drain remain in use. Temporary surge capacity may still be needed if existing capacity cannot accommodate the replacement.

The deliberate tradeoff is that ordinary eviction-based node drain cannot remove the sole healthy Runtime while this budget is binding. Planned node maintenance needs an approved relocation/overlap or a temporary budget change with an explicit availability plan. This policy can retain an underused node and forgo consolidation savings. It does not prevent abrupt node loss, forceful termination, or downtime from a misbehaving Runtime. No uninterrupted WebSocket guarantee is made.

`karpenter.sh/do-not-disrupt` would also veto consolidation but adds a Karpenter-specific pod lock without an advantage over the existing chart's standard budget here. NodePool `WhenEmpty` would prevent underutilized consolidation for every workload in the Application pool; its current source-owned management path is unverified and it is broader than this correction. Global cost optimization remains enabled.

Use the ordinary Porter server dry-run. After deployment, verify the matching PDB reports desired healthy one and no allowed disruption while Runtime has one ready endpoint. Do not perform a destructive eviction test against the sole live serving instance. The same policy is rendered for dev, staging and production as its source is promoted. Singleton Core protection is outside this change. A merge to main is not a production deployment; use the protected completed-beta promotion and verify each actual deployment separately.
