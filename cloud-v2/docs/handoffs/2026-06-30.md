# Cloud V2 - Handoff (PR #3272)

PR: https://github.com/Mentra-Community/MentraOS/pull/3272

**What it is:** Cloud V2 console/admin/portal, plus a miniapp registry (signed publish), plus preinstall to mobile auto-update. Also includes WorkOS PKCE console/CLI login, the `oemId` to `tenantId` rename, runtime reconnect fixes, and CI/CD for dev/staging/prod.

## Environments and CI/CD (now wired)

Each environment is its own Porter app, its own Doppler config, and its own database. Pushing to the matching branch auto-deploys it (the image is tagged with the git SHA via Porter):

| Env | Branch (auto-deploy) | Porter app | Backend | DB (Doppler config) |
|---|---|---|---|---|
| Dev | `dev` | `cloud-dev` | `core.dev.us-west-2...` | `cloud-v2 / dev_aws` |
| Staging | `staging` | `cloud-staging` | `core.staging.us-west-2...` | `cloud-v2 / staging` |
| Prod | `main` | `cloud-prod` | `core.mentraglass.com` | `cloud-v2 / prod` |

Debug is a separate, older app. Each env reads its own secrets and DB from its own Doppler config, so the environments are isolated.

Caveat: the Dev server is currently running my branch, not the `dev` branch. This resolves once I merge to `dev` and `dev` auto-deploys.

## Consoles: admin, portal, dev console

Three separate single-page apps under `cloud-v2/websites/`, all on the same shared design system (`AppShell` + `components/ui/*`) and authenticated with WorkOS. Each talks to its own Core API prefix.

| Console | Code | Who uses it | Core API |
|---|---|---|---|
| Dev console | `cloud-v2/websites/console` | Developers: create miniapps, publish releases, manage API keys / CLI | `/api/console/*` |
| Admin console | `cloud-v2/websites/admin` | Mentra staff: review/approve submissions, manage the preinstall registry, audit | `/api/admin/*` |
| Enterprise portal | `cloud-v2/websites/portal` | Enterprise customers: register orgs + trusted issuers (BYO auth) | `/api/portal/*` |

Deploy: each site builds and ships to Cloudflare Pages via `.github/workflows/cloud-v2-pages.yml` (which runs `cloud-v2/scripts/deploy-pages.ts <env> <site|all>`) on `dev`, `staging`, and `main`, or via manual `workflow_dispatch` (pick env + which site). Each environment is its own Pages project: `mentra-console2-{env}`, `mentra-admin-{env}`, `mentra-enterprise-portal-{env}`. Known custom domains: dev console (dev) is `console2.dev.mentraglass.com`; admin (prod) is `admin.mentraglass.com`.

### How a console reaches the right Core (per env)

The SPA bundles are environment-agnostic. They never hardcode a cloud URL; they call same-origin relative paths (`/api/console/*`, `/api/admin/*`, `/api/portal/*`). The environment is resolved by a proxy in front of Core, not in the frontend:

- Each site ships a Cloudflare Pages Function at `cloud-v2/websites/<site>/functions/api/[[path]].ts`. It catches `/api/*`, rewrites the path and query onto `CORE_URL`, forwards method/headers/body (drops `host`, adds `x-mentra-public-origin` so Core knows the public origin for cookies and redirects), and relays the response. So the browser only ever talks to its own Pages origin.
- `deploy-pages.ts` sets `CORE_URL` as a per-project Pages secret at deploy time, one value per environment: dev is `https://core.dev.us-west-2.mentraglass.com`, staging is `https://core.staging.us-west-2.mentraglass.com`, prod is `https://core.mentraglass.com`. That single secret points each Pages project (and therefore each console env) at the matching Core.
- Local dev mirrors this: each site's `src/index.ts` runs a small bun server that proxies `/api/*` to whatever `CORE_URL` you point it at (it logs `Proxying /api/* to <coreUrl>`), so local behaves like a deployed console.

Net: to move a console between clouds you change one thing, the `CORE_URL` secret on that Pages project; the frontend code and the `/api/*` paths never change. The static `_redirects` (`/* /index.html 200`) is just the SPA history fallback; the `/api/*` Function takes precedence for API calls.

## Auth: WorkOS (consoles/CLI) vs Supabase (app)

- Dev Console, Admin, Portal, and the CLI use WorkOS (AuthKit plus PKCE). We use WorkOS because it gives us organizations, org invites and roles, and CLI/SSO auth out of the box, so we do not have to build all of that ourselves.
- The MentraOS app (mobile/glasses) still uses Supabase, unchanged. The cloud-v2 token exchange verifies the Supabase session and mints the runtime token.

So: WorkOS for the developer and B2B surfaces, Supabase for the consumer app.

## Miniapp backends and the auth package (Merge example)

A miniapp backend verifies the per-miniapp token that Cloud Core mints, using `@mentra/auth` (`cloud-v2/packages/auth`). The on-device miniapp calls `session.auth.fetch(...)`, which attaches a short-lived Ed25519 token that is audience-pinned to the miniapp's packageName. The backend runs `createMentraAuth({ packageName }).hono()` as middleware; that fetches Mentra's public keys (JWKS) and checks the token's signature, issuer, audience, and expiry.

Important gotcha: every environment (prod, staging, dev, debug) signs miniapp tokens with a different key but reuses the same `kid`. So a backend that checks only one environment's JWKS will reject tokens minted by any other environment (same `kid`, different key, signature fails, 401). `@mentra/auth` now ships a multi-environment fallback (issue 017): it tries prod, then staging, dev, debug, and accepts the first that verifies. A backend gets this for free by calling `createMentraAuth({ packageName })` with no `jwksUrl`. Do not set `MENTRA_AUTH_JWKS_URL` to a single environment unless you really want to lock that backend to one environment, because that env value overrides the fallback.

How Merge is deployed (the reference example for any miniapp backend):
- Source: `miniapps/merge` (on-device miniapp in `miniapp/`, backend in `backend/`). The on-device code posts to `merge3.mentraglass.com/api/insights`.
- CI/CD: `.github/workflows/merge-prod.yml` and `merge-dev.yml`, currently triggered on push to `codex/console2-scaffold`. They `porter apply miniapps/merge/porter.{prod,dev}.yaml` (Porter project 15081, cluster 5783).
  - `merge-prod` is Porter app `merge-prod` at `merge3.mentraglass.com`, Doppler `local-merge / prd`.
  - `merge-dev` is Porter app `merge-dev` at `merge3.dev.mentraglass.com`, Doppler `local-merge / dev`.
- The Merge Dockerfile (`miniapps/merge/docker/Dockerfile`) builds from the repo root and compiles `@mentra/auth` from source (`COPY cloud-v2/packages/auth` then `bun run build`), so workspace changes ship without an npm publish.

Real-world fix (2026-06-30): production Merge showed "AI offline backend" (a 401) because the phone's cloud-v2 core was staging (staging-signed token) while the Merge backend was pinned to one environment's JWKS. Fixed by deploying the new `@mentra/auth` fallback to `merge3` and removing the `MENTRA_AUTH_JWKS_URL` pin from the `local-merge` prd and dev Doppler configs. Confirmed on a real Pixel 8: Merge returns insights again, no more `backend 401`. See `docs/issues/017-auth-jwks-multi-env-fallback`.

## CLI: build and publish a miniapp to the registry

`@mentra/cli` (bin `mentra`, at `cloud-v2/packages/cli`). Until it is on npm, run it via the env wrappers from `cloud-v2/`. Each wrapper points the CLI at that env's Core, console, and DB:

- `mentra:dev` is Dev, `mentra:staging` is Staging, `mentra:prod` is Prod, `mentra:local` is local.

```bash
# from cloud-v2/  (targets Dev)
bun run mentra:dev login                                   # sign in (WorkOS) + register signing key
bun run mentra:dev org init                                # one-time: org + package prefix
bun run mentra:dev miniapps create com.yourorg.weather     # reserve a package name
bun run mentra:dev publish --cwd ~/code/weather-miniapp    # build + pack + SIGN + upload a release
bun run mentra:dev releases submit com.yourorg.weather <releaseId>   # submit for review
# admin then approves/publishes (Admin console or admin API)
bun run mentra:dev admin preinstall publish -r com.yourorg.weather@0.1.0 -e dev   # phones auto-install/update
```

- Local dev loop: `bun run mentra:dev dev --cwd ~/code/weather-miniapp`
- Two CLIs: `mentra-miniapp` creates and builds miniapps; `@mentra/cli` wraps it and adds login, publish, and registry.

## Notes and open items

- Several dev Doppler configs exist (`dev`, `dev_aws`, `dev_per`, `dev_deb`). `cloud-dev` and `mentra:dev` use `dev_aws`. Confirm that is the canonical one so nobody points at the wrong DB.
- PR #3258 ("sync model indexes on boot") fixes the stale-index problem the identity rename caused. Recommend merging so prod and staging self-heal on boot.
- Logging: cloud-v2 has no BetterStack shipping yet (no Vector DaemonSet). App logs go to pod stdout only, so use `kubectl logs` or `porter logs` for now.
- Enterprise session refresh (PR #3272 review P1) is fixed: `refreshSession` now validates enterprise tenants against `EnterpriseOrg` (status `active`), not only `OemModel`, so enterprise users no longer get logged out after the first access-token expiry. Follow-up gap: there is currently no way to actually disable an enterprise org (no `status` setter / admin lever), so enterprise sessions have no working refresh-time kill-switch yet. The only existing enterprise off-switch is disabling an individual trusted issuer (`setTrustedIssuerEnabled`), which blocks new logins but not refresh. Tracked as item 1 in `docs/issues/018-pr-3272-review-followups`.
